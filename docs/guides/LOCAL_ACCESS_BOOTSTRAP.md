# Local Access Bootstrap

The local access-bootstrap workflow creates the first Labby owner, default
Project, published Loadout assignment, and a short-lived project credential
without requiring OAuth. It is intentionally split into an offline preparation
phase and an online consume phase. Possession of the generated proof—not
loopback access or being the first requester—is the sole eligibility check.

## Before you begin

- Stop the Labby daemon before `prepare`, `recover`, or offline `cleanup`.
- Choose an existing enabled protected route that names an already-published
  Loadout. Bootstrap never creates or silently activates gateway configuration.
- Choose two new absolute paths in owner-only directories. Neither output may
  already exist.
- Keep the proof bundle and credential file out of shell arguments, logs,
  terminals, evidence bundles, and source control.

The daemon and offline commands share the installation lifecycle lock. A
running daemon is the only online journal writer and cleanup executor; the CLI
never mutates journal state or deletes files after sending an HTTP request.

## Prepare offline

```bash
labby setup access-bootstrap prepare \
  --proof-file /secure/new/labby-bootstrap-proof.json \
  --credential-file /secure/new/labby-project-credential \
  --organization-name "Example Org" \
  --project-name "Default Project" \
  --subject local-operator \
  --loadout-id production \
  --route-id operator \
  --resource https://mcp.example.com/operator \
  --scope lab:read \
  --scope lab:admin \
  --ttl 600
```

Preparation canonicalizes the complete request, generates independent proof
and credential secrets, writes a secret-free fsynced recovery journal, and
publishes both outputs without overwrite. On Unix the files are owner-only,
opened without following symlinks, single-link checked, and recorded by parent
and file device/inode plus digest. Access-bootstrap prepare is currently
supported on Unix hosts. Windows prepare explicitly fails closed until Labby
can apply an owner-only ACL at creation and delete through a verified open
handle/file ID; it never falls back to path-only publication or deletion.

The credential is generated by the client. The server stores and compares only
its canonical digest and never receives or returns the plaintext credential.

## Consume online

Start the daemon, then submit the stored prepare by public ID:

```bash
labby setup access-bootstrap consume --prepare-id PREPARE_ID
```

The client securely reopens the exact journaled files, bypasses ambient proxy
configuration, and submits the identical normalized manifest with
`X-Labby-Bootstrap-Proof`. The daemon admits only a direct loopback or Unix
peer with literal Host/Origin authority and no forwarding headers.

Consume acquires authority in this order:

1. bounded pre-auth request admission;
2. immutable published Loadout/route policy lease;
3. the bounded access-runtime writer;
4. one SQLite `IMMEDIATE` transaction.

The transaction creates the owner, Project, membership, published Loadout
assignment, external and credential links, audit record, and generation-bound
credential, then consumes the proof. No filesystem or network operation occurs
while SQLite is held. Journal advancement occurs only after the transaction
and policy lease are released.

If the response is lost, the CLI probes the exact credential and retries the
same proof, request digest, and idempotency key. A changed retry conflicts; an
identical committed retry reports the existing metadata without issuing a new
secret.

## Status and cleanup

```bash
labby setup access-bootstrap status --prepare-id PREPARE_ID
labby setup access-bootstrap cleanup --prepare-id PREPARE_ID
```

Online status and cleanup are proof-authenticated requests to the daemon.
Responses contain public metadata only: status, prepare ID, and—after
successful consume—the credential ID. Unknown, malformed, expired, replaced,
or mismatched inputs use the same denial response and reveal no record state.

Cleanup commits durable proof and credential tombstones before touching either
file. It then deletes only the exact journaled identity through the verified
parent/file handle. Replacement, sharing, permission, link, or identity drift
leaves the tombstone authoritative and reports
`manual_file_cleanup_required`; Labby never deletes an unverified path.

## Offline recovery

When the daemon is stopped and the lifecycle lock is available:

```bash
labby setup access-bootstrap recover --prepare-id PREPARE_ID --complete
labby setup access-bootstrap recover --prepare-id PREPARE_ID --revoke
labby setup access-bootstrap cleanup --prepare-id PREPARE_ID
```

`--complete` is allowed only for the exact unexpired prepared files while the
access store remains pristine. `--revoke` permanently tombstones the reserved
proof and credential identities before exact cleanup. Replaced or unverifiable
files are never activated or automatically removed.

On daemon startup, authoritative database state wins over stale journal state.
A committed consume with a stale `proof_active` journal advances to consumed;
partial or expired preparation is completed only under the same pristine and
exact-identity checks, otherwise it is tombstoned. Tombstones are consulted by
proof activation and credential verification, so surviving plaintext cannot
revive authority.

## Credential lifecycle and browser sessions

Authenticated product credentials may use:

- `POST /v1/access/credentials` to issue an equal-or-narrower credential;
- `GET /v1/access/credentials/self` for exact self-introspection;
- `DELETE /v1/access/credentials/{credential_id}` for authorized revocation;
- `POST /auth/local-session` to create a source-bound HTTPS browser session;
- `DELETE /auth/local-session` with the session CSRF token to log out.

Every operation is private/no-store and non-enumerating. Credential issuance
uses a client-generated secret/digest and cannot amplify scopes or extend past
the source expiry. Browser sessions retain issuer, source credential ID and
generation, and expiry; every authenticated request revalidates the access
store and current published policy. Access-store busy or unavailable states
fail closed.

## Security boundaries

- Do not expose proof routes through a reverse proxy or remote listener.
- Do not copy proof or credential contents into tickets, chat, test output, or
  crash reports.
- Do not reuse output paths or attempt manual database repair.
- Treat `manual_file_cleanup_required` as a safe denial state, not permission
  to make Labby unlink a changed path.
- Product credentials, OAuth tokens, browser cookies, and the static HTTP token
  are different credential classes and are never interchangeable.
