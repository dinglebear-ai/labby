# TYPES — wire, Rust, and TypeScript views of the same shapes

Three representations of one contract. This file exists so a change to one is never made
without seeing the other two.

| Layer | Where it lives | Audience |
|---|---|---|
| **Wire (JSON)** | MCP `tools/list` + `tools/call` frames | Any MCP client |
| **Rust** | `crates/labby/src/mcp/`, `crates/labby-codemode/`, `crates/labby-gateway/` | Labby internals |
| **TypeScript** | Generated `.d.ts` in the Code Mode sandbox | The model writing sandbox code |

---

## 1. Wire types

### 1.1 A listed tool descriptor (after this change)

```jsonc
{
  "name": "gateway",
  "description": "Manage upstream MCP servers…",
  "inputSchema":  { "type": "object", "properties": { "action": …, "params": … } },
  "outputSchema": {                                    // ← new for builtin tools
    "type": "object",
    "properties": {
      "ok":      { "const": true },
      "service": { "type": "string" },
      "action":  { "type": "string" },
      "data":    { }
    },
    "required": ["ok", "service", "action", "data"],
    "additionalProperties": true
  }
}
```

`outputSchema` is omitted entirely when absent (`skip_serializing_if = "Option::is_none"`),
so the change is purely additive on the wire.

> **Scope caveat.** Builtin service tools are suppressed from `tools/list` whenever Code Mode is
> enabled (`handlers_tools.rs:135-137`), so this descriptor — and its new `outputSchema` — is
> what a **Raw-mode** client sees. Under Code Mode only `server_logs` remains. See SPEC §2.1.

### 1.2 A success result

```jsonc
{
  "content": [ { "type": "text", "text": "{\"ok\":true,\"service\":\"gateway\",…}" } ],
  "structuredContent": {
    "ok": true,
    "service": "gateway",
    "action": "gateway.list",
    "data": { "upstreams": [ … ] }
  },
  "isError": false
}
```

The text block is the serialization of the same value in `structuredContent` — required by
CONTRACT §C2.1, and the 2025-06-18 backward-compatibility recommendation.

### 1.3 An error result

```jsonc
{
  "content": [ { "type": "text", "text": "{\"ok\":false,…}" } ],
  "structuredContent": {
    "ok": false,
    "service": "gateway",
    "action": "gateway.lst",
    "error": {
      "kind": "unknown_action",
      "message": "unknown action `gateway.lst` for service `gateway`",
      "contract_version": 1,
      "origin": "discovery",
      "recovery": { "action": "rediscover", "same_arguments": "never", "guidance": "…" },
      "side_effects": "none_expected",
      "valid": ["gateway.list", "gateway.add", …],
      "hint": "gateway.list"
    }
  },
  "isError": true
}
```

Not covered by `outputSchema` — deliberately (CONTRACT §C3.2). Note the exemption for `isError`
results is **ecosystem convention, not spec text**, and the official TypeScript SDK client
currently validates error envelopes against the success schema and throws `-32602`
(fix pending in [typescript-sdk#1945](https://github.com/modelcontextprotocol/typescript-sdk/pull/1945)).

## 3. TypeScript types (Code Mode sandbox)

This is where output shapes matter most: under Code Mode, raw tools are **hidden** from
`tools/list`, so the model never sees their `outputSchema` as MCP metadata. It sees generated
TypeScript instead. That is the whole reason scope item 3 of the issue exists.

Generated by `generate_tool_types` (`crates/labby-codemode/src/ts_signatures.rs:27-75`) for
each catalog entry.

### 3.1 With an upstream output schema

```typescript
type GithubListTagsInput  = { repo: string; per_page?: number };
type GithubListTagsOutput = { tags: { name: string; commit: string }[] };

interface CodemodeGithubTools {
    /** List tags for a repository. */
    list_tags(params: GithubListTagsInput): Promise<GithubListTagsOutput>;
}
interface CodemodeTools { github: CodemodeGithubTools; }
declare var codemode: CodemodeTools;
declare function callTool(id: "github::list_tags", params: GithubListTagsInput): Promise<GithubListTagsOutput>;
```

### 3.2 Without one

`json_schema_to_type(None)` returns the literal `"unknown"`
(`ts_signatures.rs:77-83`), so the generated type is:

```typescript
type GithubListTagsOutput = unknown;
```

`unknown` — not `any`, not a guess. **Labby never synthesizes an output schema it was not
given**, which is the right honesty posture.

> **Correction.** An earlier draft said `unknown` "forces a narrowing check in sandbox code."
> It does not force anything. The sandbox executes plain JavaScript in QuickJS/javy and the
> `.d.ts` is never compiled or type-checked — it is advisory text an LLM may or may not honor.
> Two further gaps compound this: `codemode.search` results carry no `dts` and no
> `output_schema` at all (`preamble.rs:227-237`), so the `signature` string names an output type
> the model has not been given; and `codemode.describe` fetches types lazily and **fails open
> silently** (`preamble.rs:389-401`) — on error the whole TypeScript section is omitted with no
> field marking the degradation, so a type-less result looks complete.

### 3.3 Snippets

`ToolDescriptor::snippet` sets `output_schema: None` and `dts: String::new()`
(`types.rs:186-188`); the signature is `codemode.run("<name>", input?)`. A snippet returns an
arbitrary JavaScript value, so no output type can be honest. Deliberate — SPEC FR-8 requires a
comment recording this, not a change.

### 3.4 What sandbox code receives at runtime

The value bound to the awaited promise is produced by the unwrap in CONTRACT §C6. The
TypeScript type is a *claim about* that value derived from the upstream's declared schema;
nothing validates the two agree at runtime — neither Labby nor rmcp 3.1.0 performs
structuredContent validation. An upstream that declares `outputSchema` and returns something
else produces a type lie the sandbox cannot detect. This is inherent to relaying upstream
metadata and is called out in CONTRACT §C5 rather than being defended against.

## 4. Cross-layer invariants

1. A tool's advertised `outputSchema` and the `structuredContent` it returns describe the same
   value, and that content is **always present** on success. Enforced by tests (AC-3), not at
   runtime — but a declaring tool that omits `structuredContent` is a hard client-side error in
   the Python SDK.
2. The catalog `output_schema` and the generated `.d.ts` output type derive from **one**
   source — the upstream's declared schema. Neither is hand-maintained.
3. Absent schema ⇒ `unknown` in TypeScript and an omitted field on the wire. Never a fabricated
   object type, never `any`.
4. Structured values cross every layer as structure. No layer serializes to text and reparses
   (CONTRACT §C8.1).
